# Stage 26：后台调度操作顺序修复

## 复审发现

Stage 25 将可能等待调度编辑锁的按钮操作分别放入独立 goroutine。这样能保持界面响应，但快速连续点击时 goroutine 获取锁的顺序不确定，例如“全部开始”后立即点击“全部暂停”，最终状态可能与最后一次点击不一致。窗口构造提前失败时，后台执行设施也需要确定退出。

## 修复

- 增加单工作协程的 `serialExecutor`，提交操作时只做加锁入队，不阻塞 UI。
- 暂停/继续、重新下载、BT 文件编辑、全部开始和全部暂停使用同一 FIFO 队列，按用户提交顺序执行。
- 窗口正常关闭时先停止 UI 投递，再排空操作队列，随后停止调度器；初始化提前返回时由 defer 关闭空队列。
- `CloseAndWait` 可重复调用，关闭后拒绝新操作。

## 验证与交付

自动化测试阻塞第一个操作，随后提交第二、第三个操作，验证关闭会等待队列完成、执行结果严格为 `1,2,3`，且关闭后不接受新操作。测试、竞态检查、便携包与回退结果见 `021-stage-26-verification.txt`。

- 便携版：`release/GhostDownloader-0.1.19-stage26-windows-x64-portable.zip`
- 增量差异：`021-stage-26.patch`，基线为 Stage 25 工作区。
- 回退脚本：`scripts/rollback-stage26.ps1`

回退仅恢复本轮两个 UI 源文件、测试文件和 README，不触碰任务数据及便携包；Stage 25 便携包继续保留。
